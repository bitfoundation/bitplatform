# Capability matrix

What BevTools can observe, how, and where it stops. The same matrix is rendered live in the About panel with
the runtime-verified status of each row (for example, whether HandleEvent activities have actually been observed on
this host). Nothing in the UI is approximated without saying so.

Legend: **Available** — works out of the box · **Partial** — works with stated gaps · **Instrumentation** — obtained by
BevTools instrumenting framework internals (dev-only reflection or wrappers) · **Integration** — the application or
library must call an API · **Runtime** — depends on framework support (.NET 10 activities/metrics) · **Unreliable** —
deliberately not shown as fact · **N/A** — not obtainable.

BevTools ships for .NET 10 and 11.

## Components

| Information | Status | How / why |
|---|---|---|
| Component instances (all render modes) | Available | Public `IComponentActivator` hook wraps any existing activator; every instance the renderer creates is registered. |
| Parent/child hierarchy | Instrumentation | `Renderer._componentStateByComponent` → public `ComponentState.LogicalParentComponentState`. Cached expression-compiled accessor; reported unavailable if the member disappears. |
| Parameters, cascading values, `[SupplyParameterFrom*]` | Available | Read on demand from attributed properties; lazy inspection; redaction by name/attribute. |
| Component state (private fields) | Partial | Read on demand; diffed per render only for the selected component (or all with `CaptureComponentStateOnRender`). Mutations that do not lead to a render are not observed. |
| Injected services with lifetime | Available | `[Inject]` properties + captured DI registrations; each instance the component received is inspectable like its state (same inspector, same redaction). |
| Source location | Available with symbols | From the app's portable PDB: the `.razor` file a component is written in (the Razor compiler's `#line` directives make it `BuildRenderTree`'s document; opened at its top), a code-behind `.cs` where its members are written, and the exact line of each event handler and callback it binds; links open them in an editor (`Ui.EditorUrlTemplate`, VS Code by default; script URLs are refused). A PDB beside the assembly is used only when its id is the one the assembly was built with; an embedded PDB is the assembly's own; on WebAssembly the hub fetches the PDB the runtime's own resource list names for this build. Without symbols (Release builds, PDBs not deployed) the location is inferred from the type name and labelled so, with the reason. On WebAssembly the PDB is fetched with the integrity hash the runtime's resource list gives, past the HTTP cache, so a PDB of an earlier build is refused; a failed download is retried, not remembered as "no symbols". After a hot reload edit the locations of the edited assembly are marked *before hot reload* (its PDB is the build's). An assembly with no file outside WebAssembly (single-file, loaded from memory) says so. Editor links are checked on the final address: a clean scheme that is not a script scheme. |
| Disposal | Partial | Detected when the renderer no longer knows the instance (checked on refresh), so timing is approximate. |
| Event handlers and callbacks it bound | Instrumentation | Read on demand from the frames of its latest render (`ComponentState.CurrentRenderTree`): DOM handlers, `@bind` change handlers, `EventCallback`s passed to child components, each named by its method (a lambda by the one component method it calls, else the method declaring it; an `@bind` handler by the method it sets through, "@bind-value → FilterBar.OnQuery", when `@bind:set` names one). A UI event in the timeline carries only the handler's name, so a bound input's event names its component: "oninput → FilterBar (@bind)". A handler bound under a condition appears exactly while the condition holds. |
| Lifecycle | Partial | Created (activator), initialized and `OnAfterRender` run (ComponentBase fields), first and last render, a queued render, disposal (noticed on refresh). `OnInitializedAsync` and the like are not timed per instance; per-type `SetParametersAsync` times come from the framework meters. |
| Render mode | Instrumentation | What the renderer assigned (`@rendermode`, `[RenderMode*]`), read on the first render. A renderer answers for a whole subtree (an interactive renderer with its own mode for every component), so a boundary is where the mode differs from the parent's: on a circuit or in WebAssembly, the interactive root. The tree marks each boundary and the inspector names the mode a component inherits and from whom. The interactive side knows the runtime it got, not that it was chosen by `InteractiveAuto`; the prerendering summary (Runtime) carries the mode as declared. |
| Component ↔ page (pick an element, outline a component, flash renders) | Instrumentation | Blazor's browser renderer keeps a logical element tree on the DOM nodes it creates (`Symbol()`-keyed children and parent, a `true` marker on attached root containers). BevTools computes a component's position as a path of logical indices from its ancestors' render trees (`ComponentState.CurrentRenderTree`: one logical child per element, text, component and markup frame; regions flattened) and the page hub follows it, checking every step's tag or node kind. A mismatch - a render not yet applied in the browser, DOM changed by script - is reported, never resolved to a guess. The keys are learned from the panel's own element (its logical parent is its component's container comment, which no physical parent can be; for a panel that is itself a root, the root's marked container). A root counts while it carries an attached mark and no detached one (a disposed Web App root keeps its preserve-content mark). The root the panel renders in is found from the panel; any other root by the kinds of its first logical children: a path that fits a single such root identifies it; identical roots are matched by position only when the page holds exactly the runtime's own, and the outline says so; identical roots of two runtimes are reported as ambiguous instead of picked. Nodes rendered through a framework component (a `CascadingValue`'s child content, `Virtualize` items) belong to the nearest application component unless *internals* is on. Static (SSR) content and nodes added by script belong to no component, and picking says so. Requires the hub (`EnableBrowserBridge`). |

## Memory and leaks

| Information | Status | How / why |
|---|---|---|
| Disposed components still alive | Instrumentation | Disposed components are remembered weakly (at most 2000); BevTools keeps no reference to them between checks. One becomes free to go once its grace period is over (10 s; 1 s for a forced check, whose collections then count) and the renderer no longer holds it - a parent's previous render tree keeps a removed child until the parent renders again, which is not a leak and resets the count. Only full (generation 2) collections after that count, and it is called retained after two of them. One exception, on a forced check: a singleton or scoped service that still references it after its disposal is evidence on its own, renderer or not. |
| What keeps it alive | Instrumentation | References checked by identity only, never values: the delegates and framework collections of the singleton and scoped services it injected (a transient one is its own, not what keeps it) and of the values cascaded to it - a handler left on an event, named by method or as a lambda that captures it, also through a subscription object such as `IOptionsMonitor.OnChange`'s; of `Microsoft.Extensions.*` services only their delegates - the JS runtime's `DotNetObjectReference` table, and its own timers that are still scheduled with a callback or state that reaches it. Each holder is read once per check, however many retained instances share it (1000 leaked rows: about 56 ms). Anything else (a static, a cache) is not found, and the finding says so. |
| Forced collection | Available | Development and single-user processes (WebAssembly, Hybrid); refused outside Development in a process that serves many users, where it would pause every circuit. |
| Memory over time, full collections, heap after each | Available | Read once a second while the panel component is on the page, open or not (the last ten minutes), and kept while capture is on - paused, no reading is added and a collection made meanwhile is not recorded: `GC.GetTotalMemory`, the count of the highest generation's collections (gen 2 on CoreCLR, gen 1 on Mono's two-generation GC), the total pause. Each full collection is a timeline event - with the heap after it as the runtime reported it (`GC.GetGCMemoryInfo(GCKind.FullBlocking)`, CoreCLR), else the heap at the first reading after it (Mono keeps no such record: its info's members throw, and are read guarded) - so a slow interaction or a long frame can be read next to the pause that came with it. Runtime → *Memory over time* draws the heap with each full collection marked. In a server process the heap is the process's, shared by every circuit, and the panel and the events say so. Exported (`memory`, at most 120 readings and the collections). |
| WebAssembly linear memory | Instrumentation | `getDotnetRuntime(0).Module.HEAPU8.length` through the in-process module - a synchronous call on the same thread - with each reading: what the runtime got from the browser; it grows and never shrinks, so its rise is how much the heap once needed. |
| A heap that keeps growing | Available | `memory.growth`: at least five full collections in ten minutes, the heap after the last at least half again the first and 20 MB more, never back near the first. What holds the objects is a heap snapshot's question (dotnet-gcdump, the browser's memory tool); retained components are found by the check above. |

## Rendering

| Information | Status | How / why |
|---|---|---|
| Render count, `BuildRenderTree` duration per instance | Instrumentation | The private `_renderFragment` of each `ComponentBase` is replaced with a measuring wrapper at creation. Components implementing `IComponent` directly are listed but not measured (shown as *not measured*). |
| Render batches (one DOM diff) | Instrumentation | Batch boundary = `RenderBatchBuilder.UpdatedComponentDiffs.Count == 0` at render start. Fallback: idle-time heuristic (flagged *Unreliable*). |
| Batch diff duration and DOM edit count | Runtime | `aspnetcore.components.render_diff.duration/size` meters (.NET 10). On Blazor Server the framework records them when the browser acknowledges the render, so BevTools matches each measurement back to the batch that produced it. Batches BevTools does not record (its own UI, renders while capture is paused) are still bookkept, so their measurements never land on an application batch. **Blazor WebAssembly compiles `System.Diagnostics.Metrics` out by default**: add `<MetricsSupport>true</MetricsSupport>` to the WebAssembly project, otherwise the About panel reports this row as *Not available* and says why. |
| Cause: parent re-render | Available* | An ancestor rendered earlier in the same batch (renderer re-applied parameters). *Needs hierarchy + batches. |
| Cause: UI event (with attribute, component, method) | Runtime | An inline lambda (`@onclick="() => Load(4000)"`) arrives as its compiled name (`<BuildRenderTree>b__0_1`); BevTools reads the lambda's IL - or its async state machine's - and names it after the method it calls when that is its only call into application code (framework calls and property accessors aside) and a method of the component: *onclick → Orders.Load (lambda)*. A second application call (a service, a local function, a base class in another assembly), none, a compiled name more than one lambda of the component and its base classes carries, a generic component, or unreadable IL keep *lambda in Orders.BuildRenderTree*. Hot reload clears what was read. The inspector's event wiring names handlers the same way. |
| Cause: UI event, how it is captured | Runtime | `Microsoft.AspNetCore.Components.HandleEvent` activity; BevTools adds an `ActivityListener` **and registers the framework's own `ComponentsActivitySource`** (`AddComponentsTracing`), which server-side rendering registers but WebAssembly and custom hosts do not. Interactions with the BevTools panel itself are excluded, a panel an extension contributes from its own assembly included: the activity names only a component type, so the registry remembers the types only BevTools' own UI rendered. Before the first activity is seen the About panel says so. An event owns the renders made while its activity runs and the batch that renders what it had queued (read from `RenderBatchBuilder.ComponentRenderQueue` when the activity stops, since the framework renders a synchronous handler's changes after stopping it); a timer or fire-and-forget task the handler started is not the event's once it has ended, although it inherits the activity. |
| Cause: navigation | Partial | `NavigationManager.LocationChanged` always; `Navigate` activity when emitted. Same ownership as a UI event: the renders of the navigation itself, not those of a timer the page it rendered started. |
| Cause: explicit `StateHasChanged` / async continuation | Partial | Everything not attributable above. The caller is not identified (no stack walk by design). |
| Forced re-render (parent re-applied identical parameters) | Partial | For the component selected in the inspector (or all, with `CaptureComponentStateOnRender`), parameter and cascading values are flattened two levels deep (≤ 25 collection items, one time budget per render) before each render and diffed against the previous captured render. A parent-caused render with no observable change is marked *forced* and counted. Delegates compare by target method, so a recreated lambda with the same body counts as unchanged. Render fragments compare by instance, and one that reads component state as it runs never counts as unchanged, so new child content is never called forced. `[BevToolsSensitive]` parameters compare as redacted. Not decided for the first captured render (nothing to compare against), nor for the first one after renders that were not compared (the component was not inspected, or capture was paused). |
| `SetParametersAsync` cost (OnInitialized/OnParametersSet) | Runtime | `aspnetcore.components.update_parameters.duration`, per component type. A type only BevTools' own UI renders - its panels, an extension's panel, the `Virtualize` of the component tree - is left out; a framework type both render (`CascadingValue`) is counted whole, since the meter names no instance. Same WebAssembly caveat as the diff meters. |
| Event handler duration | Runtime | Activity duration; also `handle_event.duration` meter. |
| Bytes allocated per render | Available where the runtime counts them | `GC.GetAllocatedBytesForCurrentThread()` read right around each instrumented `BuildRenderTree`, after BevTools' own work for the render: what the component's render fragment allocated - strings it formatted, closures and lambdas, collections - on its thread. Children render separately and count for themselves. Per render (the inspector: per render, max, last), per component and per type in the Profiler (*Allocated*, sortable, per render in each row's title) since the session or the baseline, exports (`allocatedBytes`, `maxAllocatedBytes`, `allocatedBytesSinceBaseline`; the profile's `allocatedBytes` per type), the Markdown report and each render's timeline data. Probed once at startup: a runtime whose counter does not move reports the row *Not available* rather than every render allocating nothing. Comparisons: a type allocating `MinAllocationChangeBytes` (1 KB) and `AllocationChangeRatio` (25 %) more per render regresses, fewer improves; per render, so rendering more often is not counted twice; compared only when both recordings measured. `render.allocations`: a type averaging `HeavyRenderAllocationBytes` (256 KB) per render over at least three renders in the last 30 s. An EditForm's render includes BevTools' watch of its EditContext the first time it gets one. |
| p95 render time per component and per type | Available | Nearest-rank 95th percentile of the samples each instance still holds (the last `MaxRendersPerComponent`, 100 by default), within the *since reset* window when it is on; the cell says how many samples it is of. Counts, totals and maxima come from session-long counters, so they are exact however few samples remain. |
| What one render batch rendered | Available | Profiler → a batch → its cost tree: each component under its nearest ancestor that rendered in the same batch, with its own `BuildRenderTree` time and its subtree's; same-type siblings with nothing rendered below them (a list's rows) are one row ("ProductRow ×120 instances"); at most 300 rows, with a count of the rest. Built when the batch is selected (selecting it again or ✕ closes it; clearing the timeline drops it), from the retained samples, so a batch older than the last 100 renders of its components shows what is left. *Tree* shows it as that indented table; *Time* puts the same renders on a time axis - each where its render began (the sample's start timestamp, taken just before `BuildRenderTree`, and before BevTools' state capture for a component being inspected, so such a bar starts a little early) and as long as its `BuildRenderTree` took, one row per depth among the components that rendered in the batch. The gaps between bars hold everything else: children's `SetParametersAsync` and `OnParametersSet`, the renderer's own work, BevTools' bookkeeping. When the clock could not tell the renders apart (a span of zero), they are drawn side by side in the order they started, at equal widths, and the view says it is not to scale. Bars too narrow for their name show it on hover; a bar opens its component; to a screen reader the chart is one image whose label points to the tree. At most 300 bars, in the order they started. |
| Renders per page | Available | Profiler → *Renders per page*, closed until asked and then recomputed only when something was captured since: each retained render on the page shown when it happened - the latest navigation the timeline holds at or before it (of several at the same instant, the last) - with visits, renders, render time and the three costliest components there. A navigation is dated from its first render: the router renders the new page before anything else hears of the navigation, so where no Navigate activity records it first (framework instrumentation off) the panel dates it from the render batch the router just ran. Pages are named as their navigation was (route templates; an enhanced navigation to the same path is the same page). Renders older than the oldest navigation the timeline still holds - it drops the oldest events first, and every render is one - have a row of their own. Read from what BevTools still holds: each component's last `MaxRendersPerComponent` renders and the timeline's last `MaxEvents` events; recomputed at most once a second while open. |
| Comparison of two recordings | Available | Profiler → *Compare…* with a saved export, or `BevProfileComparison.Compare(baselineJson, currentJson)` in a test. Per component type (matched by full name without assembly versions, so a stamped build version does not turn `Grid<Product>` into a new type): instances, renders, render time, max and p95 (p95 in the API and the Markdown), as *regressed* / *improved* / *new* / *gone*. Render counts are compared exactly by default (`RenderChangeRatio` tolerates some, for recordings made by hand); times only beyond 5 ms and 50 %, because they vary between runs; a type that renders as often but clearly longer is a regression. Warnings when the two windows, render modes or runtime major/minor versions differ, a registry was truncated, or an export has no profile section (read from its components, which miss components let go before it). Text from the file is reduced to one line before it reaches the panel or the Markdown. Exports carry a `profile` section that counts components already let go after `DisposedComponentRetentionSeconds`, so a long interaction still adds up. |
| What prerendering did | Instrumentation | The prerendering panel persists a bounded summary (components, render totals, slowest components, requests, errors) through `PersistentComponentState`; the interactive panel takes it back. Needs the panel in the prerendered output and `ValueAccess` Full (the summary travels in the page). The *data fetched twice* rule compares its requests with the interactive session's first 30 s. |

## State

| Information | Status | How / why |
|---|---|---|
| Registered state containers, snapshots, change history, before/after diffs | Integration | Implement `IBevStateProvider` or register an adapter (`AddBevToolsStateProvider`). Diffs compare bounded flattened snapshots (depth 3, 25 items per collection). |
| Cascading values | Available | From `[CascadingParameter]` properties. |
| bit Blex | Integration (`Bit.BevTools.Blex`) | `AddBevToolsBlex()`: one *Blex* provider - the global state of every store as JSON, diffed member by member, a change per action (`cart/AddItem`, its arguments read through the inspector at the session's value access - redacted by name and by shape, names only under `None` - nested actions part of the outer one), and restoring the state after any of them through `BlexManager.RestoreGlobalState`, on Blex's dispatcher; a restore Blex makes itself (the Redux DevTools, persistence, another tab) is a change too. The last hundred states are kept. |
| Time travel (restoring state) | Integration | Through the provider's own contract, never by BevTools writing application objects (restoring an arbitrary graph is unsafe): a provider that implements `IBevStateRestorer` gives each change a `RestoreToken` (`BevStateChangeInfo`) and restores itself when asked. Offered only in Development or a process that serves one user, like a forced collection; the panel and About say so elsewhere. A token is kept only for a provider that can restore, exported only as `restorable`. The restore is a timeline event linked to the change, and the provider's own change notification records the new state. |
| Change details and search | Available | Each change's `Detail` (what the action was about: *Add · Quantum Lamp 3*) in the history and the diff; the State filter finds providers by name and changes by action, detail or member. |

## Forms and validation

| Information | Status | How / why |
|---|---|---|
| Forms on the page: model, owner, fields, modified, changes per field | Instrumentation | Each `EditForm`'s EditContext (`_editContext`) or an input's, watched from the EditForm's first render and again when it gets a new EditContext (a form reset after submit); held weakly, and forgotten - BevTools' handlers removed - once the EditForm or input is disposed. Field states from `_fieldStates`; changes counted from `OnFieldChanged`. Values are never read. At most 200 forms at once, and the panel says when more were alive. |
| Each validation and its outcome | Instrumentation | `OnValidationRequested`. BevTools moves its handler to the end of the list at the first validation, so from the second on the outcome is read right after every validator ran and before `OnValidSubmit` runs; the first is read once the work yields. Recorded on the timeline with its trigger. |
| Validation messages | Available | `GetValidationMessages` per field, redacted; hidden under ValueAccess None, since a parse error can repeat what was typed. |
| What validates a form, and what shows its messages | Instrumentation | The handlers of `OnValidationRequested` (`DataAnnotationsValidator`, a custom validator), without BevTools' own and without the framework's form mapping (an EditForm with a `FormName` on a server subscribes to report form-post binding errors, which checks no attribute); `ValidationSummary` and `ValidationMessage<T>` among the handlers of `OnValidationStateChanged` (inputs subscribe too, for their CSS class, and are not displays). |
| Rules | Available | `forms.validation`: the model has validation attributes and nothing validates the form (Validate() and OnValidSubmit always pass); a validation failed and no ValidationSummary or ValidationMessage listens. |

## Routing and authentication

| Information | Status | How / why |
|---|---|---|
| Current route: page, route values, query, layout | Available | From the `RouteView`'s public `RouteData` and `NavigationManager`; values through the inspector, the URI redacted. Without a `RouteView` in the session (the router runs during static rendering, per-page interactivity) only the URI is known, and the panel says so. |
| Matched template | Partial | `RouteData.Template` when the router fills it in (.NET 10; not every router does, the demo's interactive one does not); otherwise inferred only for a page with a single `@page`, and labeled inferred. |
| Route table with authorization, render mode, layout | Available | The `Router`'s `AppAssembly` and `AdditionalAssemblies`, read as the router reads them (exported types with `[Route]`); `[Authorize]` read by name. Without a router: the assemblies of the pages the session rendered, labeled so. |
| Navigation guards | Instrumentation | `NavigationLock` components (whether they confirm leaving the site, which callback runs before internal navigation) and the handlers in `NavigationManager._locationChangingHandlers`, each with the component that registered it. Read only: registering a LocationChanging handler of BevTools' own would make the browser ask .NET before every navigation. |
| What each navigation rendered | Available | The renders each navigation caused - every render event names the event that triggered it, and on .NET 10 a navigation is one - so later clicks and timers are not counted. Where the runtime does not report navigations as triggers, the renders from one navigation until the next, and the column's tooltip says which it is. Needs render events (`RecordRenderEvents`). |
| Redirect loops and navigation storms | Available | `navigation.loop`: at least six navigations alternating between two destinations within 10 s, or ten within 2 s - counting only navigations code made (`NavigateTo`), not a click on a link, a back/forward or one made from a UI event, so a person browsing a list and its details or a search box that writes the query string is not a loop. Read from the last five minutes of navigations by their own times, so a loop that ran while the panel was closed is found when it opens. How each navigation came about is noted from `LocationChanged` even when the router's activity recorded it (.NET 10). |
| Cancelled navigations, `forceLoad`, NotFound | N/A | No event exists for a cancelled navigation without registering a LocationChanging handler (see guards); a forced load ends the page; subscribing to `OnNotFound` could change what happens when nothing else handles it. |
| Authentication state, roles, claims, changes | Available | The scope's `AuthenticationStateProvider` (by name) as a built-in state provider; `AuthenticationStateChanged` records changes with diffs. Asking for the current state is BevTools' own work, so a provider's API call meanwhile is not recorded as the app's. Claim values follow `ValueAccess`; sensitive claim types and token-shaped values are redacted. |

## Network

| Information | Status | How / why |
|---|---|---|
| Requests via `IHttpClientFactory`: method, URL, status, duration, sizes, headers | Available | `IHttpMessageHandlerBuilderFilter` adds a `DelegatingHandler` to every pipeline, innermost so each retry is its own record; the issuing session is resolved at the outer end, so attempts made after another handler left the renderer's context are still attributed. Sensitive headers and query/fragment values redacted. |
| Hand-built `HttpClient` | Integration | Add `BevToolsHttpMessageHandler` manually. |
| The trace a request carried to the server (OpenTelemetry) | Available when the client propagates one | HttpClient's diagnostics handler writes the W3C `traceparent` header in the primary handler, below BevTools' handler, so it is read from the request once it completes: its trace id is what the server's spans and logs are filed under in a tracing backend, its parent id the client span. On a server the client propagates while an activity is current - a request made in a UI event carries one (measured on the demo's circuit: `GET /api/orders` from *onclick → Orders.Load*), one made from `OnInitializedAsync` with no activity and nothing listening to `System.Net.Http` does not; the browser's HttpClient propagates nothing by default. Only a well-formed header counts. Shown in a request's detail (*logs in it* filters the Logs panel to the same trace; a log entry's *requests in it* the other way), filterable (`trace:`), exported (`traceId`, `spanId`) and in the companion. |
| Bodies | Opt-in | `CaptureHttpBodies` (off): text bodies only (JSON, XML, forms, text, GraphQL), at most `MaxHttpBodyBytes` (16 KB), redacted at capture - a JSON or form value under a sensitive name, anything credential-shaped. Never at the cost of the request: a request body is read only when it is byte-array content (strings, forms) or JSON content (serialized into the buffer the send then uses, once), never a stream; a response body only when its length is known and within the limit (buffered as HttpClient would, so the app reads the same bytes), never a chunked body or server-sent events. Honoured only at `ValueAccess` Full, and in a process that serves many users only in Development; About says when it is set but not honoured. Each body that was not read says why. Shown in a request's detail, exported, in the companion. |
| gRPC-Web, server-sent events, GraphQL | Partial | Told apart by content type and path (`application/grpc*`, `text/event-stream`, `/graphql`); a GraphQL operation is named from its body when bodies are captured. A request's duration is to its response headers - the body is read above BevTools' handler - which for a stream is when it started, not when it ended. |
| Originating UI event | Partial | Linked when a HandleEvent activity is executing; lifecycle/timer requests show no trigger. |
| Component that sent a request | Available | Read from the stack when the request enters the pipeline: the nearest component method, and the application method between them - *OrderRow.OnInitializedAsync via ProductApi.GetOrderDetailsAsync*. Async methods are named through their state machines (on the stack again after every await), local functions by themselves, lambdas by the method they are in; framework and BevTools frames are passed over. In an `IHttpClientFactory` pipeline it is read at the outer end, once per request, so a retry handler that awaits before sending does not lose it and every attempt carries it; a hand-built client's `BevToolsHttpMessageHandler` reads it itself. A request sent by code no component method is waiting on synchronously - a timer, a background loop, a service that awaited something of its own before sending - has no component on its stack and says so, with the reason: nothing on the stack; a continuation that another task's completion ran (on WebAssembly, without a synchronization context, completing a task runs what awaited it on the completer's stack, so the walk stops there rather than name the completer); none within the 256 innermost frames; or a stack that cannot be read (a trimmed or AOT build). A generic component is named by its definition (`GenericRow<TItem>`): a stack frame does not say which instantiation ran. Shown as *Sent from* in a request's detail, in the Trigger column when no UI event triggered it, per endpoint (the top sender, and how many others in all), in `http.per-item`'s evidence, the request filter, exports (`caller` or `callerMissing`; `callers` and `callerCount` per endpoint) and the companion. One stack walk per recorded request (`CaptureHttpCallers`, on by default; none while capture is paused; see performance.md). |
| Cancelled requests and `HttpClient.Timeout` | Partial | A request whose own token was cancelled is shown as *cancelled*, not as a failure: by the caller, `HttpClient.Timeout` or a handler in the pipeline (a resilience attempt timeout, hedging) - inside the pipeline these look the same, and BevTools, innermost, sees each attempt. Any other cancellation (a connect timeout's `TaskCanceledException`) is a failure, recorded in Errors with its inner exception's message. |
| Bursts to one endpoint (a request per keystroke) | Available | `http.burst`: one endpoint (method, path, query parameter names) - or one endpoint template whose requests each come from their own UI event - called `HttpBurstCount` times within `HttpBurstWindowMs` with different query values; the evidence names the triggering UI events and how many requests started before the previous one completed, which is when an older response can arrive last and overwrite a newer result. Exact repeats stay `http.duplicate`'s. |
| Requests per endpoint | Available | Network → *Endpoints*: one row per method, path and query parameter names, with the path segments that are ids - numbers, GUIDs, hexadecimal strings of 16 characters or more - as `{id}` (`GET /api/orders/{id}`; `/api/orders/recent` stays itself).
