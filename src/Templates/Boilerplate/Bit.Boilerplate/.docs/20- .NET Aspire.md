## What is .NET Aspire?

.NET Aspire is an **opinionated, cloud-ready stack** for building observable, production-ready distributed applications. It's a developer-first, always-free, open-source platform that helps you orchestrate complex multi-service applications with ease.

### Key Philosophy

Aspire follows a **"code-centric control"** approach where you define your entire stack in type-safe and readable. You can run locally and deploy anywhere without architectural changes.

## How .NET Aspire Benefits This Project

.NET Aspire **significantly improves both Development and Deployment**:

### 1. **Development Experience** 🚀

.NET Aspire provides an **awesome dashboard for monitoring your app during development**, giving you:

- **Real-time Logs**: See all application logs in one place
- **Metrics**: Monitor performance counters and custom metrics
- **Distributed Traces**: Track requests across services
- **Health Checks**: View the health status of all services

Additionally, it provides:

  - **DbGate** for database management (in this project)

### 2. **Deployment Flexibility** 🌐

.NET Aspire **simplifies deployment** not only to Azure Cloud, but also to:

- ✅ **Kubernetes (k8s)** (for enterprise orchestration on any provider)
- ✅ **Azure Cloud** (with automatic resource provisioning)

The same code you write for local development works across all these deployment targets!

## Aspire in This Project

### Project Structure

The Aspire orchestration is managed by:

**Location**: [`src/Server/Boilerplate.Server.AppHost/`](/src/Server/Boilerplate.Server.AppHost/)

This project contains:
- **`Program.cs`**: Defines all application resources and dependencies
- **`appsettings.json`**: General configuration
- **`appsettings.Development.json`**: Development-specific settings (credentials, passwords)

### AppHost Configuration

`Program.cs` is the list of what your application is made of - one line per resource. Each of those lines is a small
extension method in `Infrastructure/Extensions/IDistributedApplicationBuilderExtensions.cs`, which is where the actual
container configuration lives:

```csharp
var redisCache = builder.AddRedisCache();
var redisPersistent = builder.AddRedisPersistent();
var sqlDatabase = builder.AddSqlServer();
var keycloak = builder.AddKeycloak();
```

Things worth knowing when you read it:

1. **One extension method per resource**: open the method to see how that resource is configured. The ones with an
   Azure equivalent - SQL Server, PostgreSQL, both Redis instances, Blob Storage - are written as
   `AddAzure…(...).RunAsContainer(...)`, so the same code runs a container locally and provisions the real Azure
   resource when you deploy; remove the `RunAsContainer` to switch. The rest (Keycloak, MySQL, SQLite) are plain
   container/file resources with no such pairing
2. **Management UIs**: DbGate for SQL Server, pgAdmin for PostgreSQL, phpMyAdmin for MySQL, sqlite-web for SQLite,
   plus RedisInsight and Redis Commander
3. **Service Dependencies**: `serverWebProject.WithReference(sqlDatabase).WaitFor(sqlDatabase)` ensures the database is
   ready before the server starts
4. **Run mode vs publish mode**: `builder.ExecutionContext.IsRunMode` is true for `aspire run` / F5 and false for
   `aspire publish` / `aspire deploy`. It is a different axis from the *environment* - a publish can target
   Development too - so anything that must never ship goes inside that block
5. **Dev Tunnels**: Allows external access to your local development server via HTTPS, and is what lets a phone or an
   emulator reach the server and report telemetry

## Important Database Management Tip

### The Challenge

There's one important detail that might take time to discover:

When the application is running, you can manage the database through **Aspire's built-in DbGate** web-based database management tool.

**However**, when the application stops:
- ❌ The database stops
- ❌ DbGate stops working
- ❌ You can't even connect with external tools (SSMS, Azure Data Studio, etc.)

This is fine for test projects, but for **real projects** where you continuously work with the database, this can be limiting.

### The Solution: Persistent Containers

**Uncomment `builder.UsePersistentContainers()`** - see the next section. That keeps the database (and every other
container) alive between runs, so DbGate and any external tool stay connected.

✅ Database remains running even when the app stops  
✅ Connect with any database tool (SSMS, Azure Data Studio, DBeaver, etc.)  
✅ Credentials are stored in `appsettings.Development.json`

The host port is allocated by Aspire, so read it from the resource's connection string in the dashboard rather than
assuming `1433`.

### Finding Database Credentials

**Location**: [`src/Server/Boilerplate.Server.AppHost/appsettings.Development.json`](/src/Server/Boilerplate.Server.AppHost/appsettings.Development.json)

```json
{
    "Parameters": {
        "sqlserver-password": "P@ssw0rd",
        "sqlserver__Comment": "The username is `sa` by default",
        "s3-rootPassword": "P@ssw0rd",
        "s3__Comment": "The username is `minioadmin` by default",
        "keycloak-password": "P@ssw0rd",
        "redis-cache-password": "P@ssw0rd",
        "redis-persistent-password": "P@ssw0rd",
        "Comment": "You might need to delete the docker volumes to apply changes to the passwords"
    }
}
```

**Default SQL Server Credentials**:
- **Username**: `sa`
- **Password**: `P@ssw0rd` (configurable)
- **Server**: `localhost` on the port the dashboard shows for the resource (only `1433` if you pinned it yourself)

## Making All Containers Persistent

By default every container (database, Keycloak, Redis, MailPit, storage and their management UIs) is re-created on each run and removed when the app host stops. Your **data** is not lost with them - the resources that need it are configured with volumes (the database, Redis and Keycloak among them), and a volume outlives the container until you delete it explicitly. What you pay is the boot-up time of every container, on every run.

There's a ready-made line at the bottom of `Program.cs` in the `Boilerplate.Server.AppHost` project that keeps the containers themselves alive and reuses them instead - just uncomment it:

```csharp
if (builder.ExecutionContext.IsRunMode)
{
    builder.UsePersistentContainers();
}
```

### Trade-offs

✅ Starting the project with `F5` / `aspire start` becomes noticeably faster  
✅ The automated tests run considerably faster, as they no longer wait for the containers to boot up and become healthy  
✅ The database keeps running when the app stops, so DbGate and external tools (SSMS, DBeaver, ...) stay usable  
⚠️ Those containers keep running (and consuming memory) while you're not debugging - stop them from **Docker Desktop** (or with `docker stop`) whenever you need those resources back, the app host will start them again on the next run  

**If this is your main project and you work on it every day, uncommenting it is recommended.**

## Important Note: Docker Execution

### How This Project Uses Docker

**For Performance Optimization**:
- ❌ `Boilerplate.Server.Api` **does NOT** run on Docker
- ❌ `Boilerplate.Server.Web` **does NOT** run on Docker
- ✅ They run **natively** for faster development experience

**Why?**
- Native execution is significantly faster than containers
- Hot reload and debugging work better
- Less resource consumption on your development machine

### Testing Linux Behavior on Windows

If you want to **test server behavior in Linux** while **still using Aspire** on Windows:

1. Open the project in **Visual Studio Code**
2. Use **Dev Containers** feature (requires Docker Desktop and Dev Containers extension)
3. Run this command in the terminal to clean previous Windows build artifacts:
   ```bash
   chmod +x ./Clean.sh && ./Clean.sh
   ```
4. Then run the `Boilerplate.Server.AppHost` project

**Result**: You can test Linux behavior while still benefiting from Aspire's features! 🐧

## Deployment with Aspire

### Supported Deployment Targets

.NET Aspire simplifies deployment to:

1. **Azure Cloud**
   - Automatic resource provisioning
   - Azure Container Apps
   - Azure SQL Database
   - Azure Blob Storage

2. **Docker Compose**
   - Generate `docker-compose.yml` automatically
   - Perfect for VPS and self-hosted environments

3. **Kubernetes (k8s)**
   - Generate Kubernetes manifests
   - Works with any k8s provider (Azure AKS, AWS EKS, Google GKE, on-premises)

### How Deployment Works

Aspire can generate deployment artifacts for these platforms based on your `Program.cs` configuration. The same code that orchestrates local development can be transformed into:

- Azure Bicep templates
- Docker Compose files
- Kubernetes YAML manifests

This ensures **consistency** between development and production environments!
